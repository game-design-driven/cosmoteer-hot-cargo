## 44. Invariants and the playthrough test

Code: `src/HotCargo/Dev/Invariants.cs` (rules), `src/HotCargo/Dev/Playthrough.cs` (playthrough commands). Test: `tests/autotest/core-playthrough.txt`. Numbers: the `Invariants` tunables section.

990. **Invariants.** A checker tests rules that must always hold while a run is active. A broken rule writes one line `ERROR invariant <name>: <details>` to `hot_cargo_log.txt`, once for each rule and subject in a game session. Every autotest fails on an ERROR line, so each test checks every rule. Telemetry records every log line (`log` event), so playtests show broken rules too. The checker only reads the game: it never changes sim state, so co-op stays in sync, and it does not show in the overlay.
991. **Tech in vaults** (`tech_count`). On each human ship, the stored tech that the game counts (`GetResourceTotal`) equals the units in its Tech Vault grids and normal storage tiles, the units that the art shows (requirements 14, 59 and 1543).
992. **Vault hits** (`vault_hit`). A health change of a vault that does not destroy it costs no tech (requirement 65): the units in the vault stay the same. The check runs after every other patch of `Part.OnHealthChanged`.
993. **Heat range** (`heat_range`, `heat_stages`). Heat stays in 0 to 100 (requirement 29), and the started stages are exactly the stages that the heat reached.
994. **Chain ships wait** (`hostile_chain_trigger`). A ship with an `hc_ch_` tag and the hunter AI (`HotCargoHunter`) does not attack the players while no chain mission is in progress: a stage mission that the players accepted, or a Return or Arrival mission, which goes straight to the log. A ship of a stage offer, with any AI, does not attack before the accept (requirement 2300). After its stage ends, a guard with the vanilla `Normal` AI may defend its post like a vanilla bounty guard.
995. **Hunters wait** (`hostile_hunter_trigger`). A hunter (`hc_hunter`) does not attack the players while heat is 0 or no stage started, unless a hunter wave spawned in this game session (a stage, a strike wave, an informant, an event or a test command). Limit for 994 and 995: "attacks" means an attack command on a human ship; a weapon that fires at a ship in range without a command does not count.
996. **Markers end with their mission** (`mission_marker`). A mission marker is a target area marker (`cosmoteer.poi_target_area`) that an objective owns (`Missions/MissionMarkers.Of`): the POI that a vanilla objective names (read from its type: every `...DoodadID` property, such as `POIDoodadID`, and every `ObjectiveTargetDoodad<POIDoodad>` property, such as the `SuggestedCollectionPOI` of DeliverResources) or the marker of a Hot Cargo objective (`IMissionMarkers`). A map ring that a mission only uses (a belt pass for Hold the Pass) is not a mission marker. When the objective that owns a marker ends (completed or failed), the marker goes, also while the mission waits for its pay; at the latest it goes when the mission leaves the log (completed, failed or abandoned) or the offer is dismissed (requirement 103) or goes away (vanilla drops an offer that expired, for example when its escort ship died; one tick later an offer in neither the log nor an offer list has gone, `MissionMarkers.SweepWithdrawn`). A marker stays while another objective in progress or an offer owns it. A save after the end has no marker: the marker is gone from the sim. Vanilla removes a bounty marker only when its ships die, so an abandoned bounty kept its marker before. The rule: a marker that an objective owned at an earlier check and that no objective in progress or offer owns in two checks in a row breaks it. Test `missions-markers-end` completes, then fails, the marker objectives of every offer of the system. Playtest 2026-11-24: the Salvage Race ring stayed after the race. A mission that ends while the players are in another system loses its markers on the next arrival in its system (requirement 2250). Limit: a marker whose mission ends before its first check is not seen.
997. **Rivals are symmetric** (`rival_symmetric`). When accepting offer A dismisses offer B, accepting B dismisses A, and no offer names itself or a copy of itself (requirement 103). One offer can sit in several offer lists as copies with the same `MissionID`, so the check compares offers by `MissionID` (`ContractBook.RivalsOf`). A new offer counts in its rules rival group on both sides before the scan saves its terms (within a second). Test `contracts-contracts` checks a new Mining Escort offer and the Sun Mining offers of its group (`ore_claims`) with the scan paused.
998. **Shown text** (`shown_text`). Text that the game shows has no raw markup: no tag in a renderer without XML formatting, no escaped tag (`&lt;`) in a renderer with XML formatting, and no unfilled `{placeholder}`. The check runs at the end of the frame for each text renderer whose text or XML switch changed in that frame. It reads widgets only.
999. **Heat sources** (`heat_source`). Every heat change comes from a documented source (TELEMETRY.md, "Sources and causes"): a change whose caller matches no source rule breaks the rule. Limit: it runs only while the Telemetry `Heat` category is on.
1000. **Switch and cost.** `Invariants.Enabled` (default on, in tests and in play) turns every rule off. The rules that read the whole system run every `Invariants.CheckSeconds` (default 1) game seconds; the vault, heat source and text rules run at their event. Telemetry measures the cost with the rest of the mod.
1001. A rule that a correct game breaks is a wrong rule: fix the rule in place, and fix its line here. A rule that a real bug breaks stays, and the bug gets fixed.
1002. **New hunters are hostile** (`hunter_spawn_hostile`). A hunter that the mod spawns (`HunterSpawner.SpawnWave`) has no human player index and is an enemy of every human ship (requirement 33). Playtest 2026-11-13: new hunters copied the index of a hunter ship that the players owned, and joined their fleet. The check runs at each spawn. The players can take a hunter ship over later; that does not break the rule.
1003. **Hunters are one side** (`hunter_one_side`). The hunters of a system, live and in stasis, have one player index (requirement 33). Wrecks and hunter ships that the players took over do not count.
1004. **Playthrough test.** `core-playthrough` plays a new single-player run the way a person does, with no godmode, no teleports, no test damage and no free money or tech: ship AI tactics on with a preset, fly to the nearest station, accept the local fight with the lowest threat (the lowest tier, then the fewest targets with the Disable tactic, because the starting ship carries no steel to rebuild shot thrusters and control parts, then the nearest), right click its target ship again every 20 seconds as it moves (the ship AI fights) until the fight steps end, fly back (slowly, when the thrusters are shot), collect the reward (a vanilla bounty ends with a ReceiveRewards step, `sysgen_bounties.rules`: call the station, receive payment), sell 1 tech, hire crew for the free beds (the hire tab's hire-all button: a fire in the fight can kill crew), repair with the build window's repair button and buy what it costs (again every 20 seconds while parts are hurt, also for what the queued repairs still wait for), unlock and build a small hyperdrive, buy steel, coil and hyperium, repair again if a part is hurt (a scorched drive is off and counts no fuel), wait until the crew carry the hyperium into the drive by themselves, fly to the relay toward an unvisited system with the fewest enemy ships near the straight route (live or in stasis), then the nearest, order the relay jump and press ENGAGE. It passes when the run reaches sector 2 with tech above 0 and no invariant broke.
1005. Each playthrough command (`pt_*`) sends the input of one player click: a right click order (`MPEnqueueCommandsInput`), a comms button (`MPAcceptMissionInput`, `MPMissionPaymentInput`, `MPBuyTechInput`), a trade window transfer (`MPMoveResourcesInput`), or a build window button (`MPUpdateShipInput`: build confirmation, repair all). The headless slot draws no frames, so after the jump the test unpauses the sim (journey-jump.txt).
1006. The playthrough runs in the full suite only. Its script asks for a longer timeout with a `# timeout: <seconds>` line, which every runner reads (`test_timeout` in `scripts/autotest-lib.sh`: the PC, the headless sim and the CI shards).
1007. **Test clock.** While a run is active, has no result yet and its sim ticks, script waits (`wait`, `waitfor` timeouts) and the repeated orders of the `pt_*` commands count the run's game seconds, so a test means the same on a loaded machine; at other times they count real seconds. Game seconds stop at a win or a loss, so a wait after the end counts real seconds. A timeout ends only after both its game and its real seconds. Each wait has a real-time budget, so a hung game still fails. `waitreal` and `waitforreal` count real seconds only, for files, the network or another process. Measured 2026-11-14 with 8 co-op sessions at once on one Mac: the hosts ran at 23 to 77 % of real time, so a real-time `wait` covered that much less of the game than the script says.
1008. **Tech only here** (`tech_elsewhere`). No tech that hunters or friendly ships hold, and no waiting tech (requirement 1554), belongs to another system: a move to another system loses it (requirement 2520). A waiting ship that just arrived counts as here until its next tick.
1009. **The sim changes only in a sim phase** (`sim_outside_phase`, `Core/SimPhase.cs`). A sim phase is a part of the frame that every co-op machine runs at the same point: the sim tick (`SimRoot.FixedUpdate`), the input tick (`SimRoot.OnInputTick`, `GameModeManager.OnInputTick`) and the execution of player inputs (`Update` of `SPManager` and `RecordableSPManager` in single player, `BaseMPManager.AdvanceNetworkTime` in co-op). All other code is frame code: UI, draw, widget callbacks, `Run.Hooks.Frame`. At the end of each phase the checker takes a fingerprint: the sim random stream, the run state hash (`CareerPatches.AddRunHash`) and the player states (money, fame). At the start of the next phase the fingerprint must be the same. A difference breaks the rule and names the parts that changed and the two phases around the change. In autotests the check also runs after each `Run.Hooks.Frame` handler and names the handler. Code that may change the sim from a frame opens its own phase with `SimPhase.Open`: test commands, the single-player debug keys and the single-player tunables reload. `Invariants.SimPhase` (default on) turns the rule off. Test `core-sim-phase` changes the run state and draws a sim random number from a frame, and expects both breaks (`invariants_expect <rule>`: breaks of that rule count in `invariants_expected` and log no ERROR). Cost, measured on the PC in the co-op session `coop-stress` on 2026-11-26: 2 to 3 µs for each phase start and each phase end, about 0.03 ms per sim tick of 4.1 ms. Limit: a change of state outside the fingerprint passes (a ship, a run state field that the run hash does not hold). A new run, another sim (a jump, a load, a resync) and work on another thread start a new fingerprint. A node jump (`GameRoot.IsDoingNodeJump`) has no check from its start to its end: vanilla builds the next system on a worker thread, and that build adds player states (issue 386). Every co-op machine runs that build at the same jump signals, so it is no desync, and a fingerprint read while the thread adds a state crashed the game ("Collection was modified"). Limit: frame code that changes the sim during a jump passes. Test `core-sim-phase` also makes a new player state from a frame (a break) and during a jump (no break).
1970. **Test speed.** Game tests run at the game speed 1 by default (`HOT_CARGO_DEFAULT_TEST_SPEED` in `scripts/autotest-lib.sh`); `HOT_CARGO_TEST_SPEED` or a test's `# speed: <x>` line changes it, and a manual CI run takes the input `test_speed`. The headless sim already runs single-player games as fast as the CPU allows (a fixed clock step per frame), and co-op sessions run in real time but are CPU bound, so a higher game speed adds no throughput. Measured on 2026-11-23, full suite in CI, 145 tests, summed test seconds: speed 1: 9,505 single-player and 1,609 co-op, all pass; speed 2: 10,084 and 1,573, 6 tests fail; speed 4: 10,838 and 1,679, 9 tests fail.
