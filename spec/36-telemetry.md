## 36. Telemetry

Logs and telemetry of game sessions, for analysis of test runs and playtests. TELEMETRY.md holds the schema and the tools. Code: `src/HotCargo/Telemetry/`. Numbers: the `Telemetry` tunables section.

530. Each game session writes one JSONL file `<run id>__<session id>.jsonl` in the `telemetry` folder of the mod. A session is one game from its start or load until it closes. `scripts/deploy.sh` and the player installers keep the folder (requirement 1989).
531. A run has an ID that the career save keeps (path `HotCargoTelemetry`), so a loaded game continues it. A new career gets a new ID. The first line (`session.start`) holds the run and session IDs, the game version, the mod version with its git commit, the tunables hash, a hash and a full copy of the tunables in effect, the galaxy seed, the map size, the difficulty settings, the player count and the autotest label.
532. Every event has the event name, real time, game time of the run, sim time of the session, sector index, system, tier, sector type, heat and fleet tech count.
533. **Run**: new run, load, save, jump (with the stay and its time use), system entry (with the previous stay, its time use and its missions), win, loss with the reason, and the session end with its reason.
534. **Heat**: every heat change with its source and caller, time and trail heat summed over `AccrualSeconds`, stage starts and strike waves. **Tech**: count changes with a cause, tech value steps and vault hits. Notoriety is in the tech value events and the snapshots.
535. **Economy**: money and fame changes with their source and caller, reputation changes, and station trades with the unit price. A blueprint unlock shows as source `tech_unlock` (requirement 1586); any other money change outside `PlayerState.AddMoney` shows as source `untracked`.
536. **Missions**: offers with their contract terms, accepts, and the end with the result (spec 166 names), the time to finish and the sell-out flag. **Story**: event pages, choices with the rolled outcome, results with their effect lines, and chain starts and stages.
537. **Combat**: a census at the first visit of a system, every later non-player ship spawn, derelict ships by side, ships that leave the system, human crew deaths, and damage summed by the side of the damaged ship. **AI**: the strategy module that drives each AI ship, with a switch event at most every `AiSwitchMinSeconds` per ship and `AiEventsPerMinute` in total, and sums of every module, tactic and focus fire decision in the snapshots.
538. **Snapshots**: every `SnapshotSeconds` game seconds, at each jump and at the run result: the run state, money, fame, contracts, the value, firepower, parts, vaults and crew of each player ship, and the time use of the current stay (requirement 1762).
539. **Performance**: every `PerfSeconds` real seconds: frame time (mean, percentiles, maximum, slow frames), sim tick time, GC counts and pause time, memory, and the time and share that telemetry used. **Co-op**: player count changes, desyncs and co-op game loads (joins and resyncs).
540. Each category has a switch in the `Telemetry` tunables section, and `Enabled` turns all telemetry off. The section is validated with the other tunables (spec 53).
541. Telemetry never blocks a frame or a sim tick: game threads add a line to a list, and a background thread writes it once per second. A file that reaches `MaxFileMegabytes` continues in a part file. At session start the oldest files go until the folder is below `MaxFolderMegabytes`. More than 200,000 lines that wait are dropped and counted.
542. Telemetry measures its own time on game threads and reports it. Target: well below 1 % of the real time of a session, which is the share of frame time at a steady frame rate. The autotests check it.
543. Telemetry reads game state only. It never changes the simulation and uses no sim random source, so each co-op machine writes its own file, with its own switches, without a desync. A co-op client also sends a copy of its files to the host (requirement 1592).
544. `scripts/pull-telemetry.sh [SLOT...]` copies the files of the main slot and the test slots to `../.telemetry/`, with the client copies in `players/`. `tools/telemetry` (`uv run hc-telemetry`) writes a markdown and a self-contained HTML report: per sector time, missions and time use by activity, heat curve and sources, money and power over time by tier, tech sales, losses, hunter outcomes, AI module frequencies and performance. `scripts/autotest-all.sh --telemetry` pulls and reports after a test pass.
545. Every autotest makes telemetry with the script name as its label. `telemetry-basic` checks the categories, each time use activity (requirement 1763), a save and load and the overhead; `telemetry-run` is a scripted run over three systems that ends with a win and checks that each event kind shows. It shields the player's ships (test command `shieldplayers`), so it does not depend on survival.

Playtest 2026-11-14 (run `r20261114-212053-eb3e`) showed gaps: wreck pieces counted as ships, captures and ships left behind did not show, and some numbers were wrong. Requirements 1580 to 1591 close them. Pure rules: `Telemetry/TelemetryModel.cs`.

1580. **One ship, one side, one wreck.** Vanilla turns each piece of a broken ship into its own ship and junks each one (`SimModeManager.OnShipSplit`). A split adds its pieces to the lineage of the ship. `combat.destroyed` fires once per lineage, when its last live piece becomes a wreck, with the name, side, value and tags of the ship before it broke. Every event names a piece by the side of its ship, so a hunter stays a hunter in damage, AI, spawn and wreck events.
1581. **Fleet changes.** `combat.captured`: a ship that becomes a player ship, with its side before it was a wreck or another side's ship, how (`claim`, `joined`, `other`), its value, hyperdrive and tech. `combat.fleet_left`: a player ship that stays behind at a jump, is gone after a co-op resync or join (compared with the previous session in the same process, in the same system), or becomes another side's ship without a wreck.
1582. **Jump ships.** `run.jump` lists the ships that jump (in jump limbo) and the human ships that stay in the old system. Each has its hyperdrive, hyperium, drive capacity, the vanilla fuel cost of the jump path (`FtlManager.GetTotalFtlMapJumpFuelCost`), too big (cost above capacity), tech and parts.
1583. **Diplomacy.** `dip.hail` (vanilla `AIHailPlayer`: offer or demand of surrender, with the price), `dip.surrender` (vanilla `MPShipSurrenderedInput`: who gives up, the price, accepted), and `dip.deal` (each Hot Cargo hail choice through `Deals.Decided`: offer, amount, price, chance, roll, accepted). Each has the odds, confidence, bravery, stance and allies of the risk model (requirements 1520 to 1524). Switch `Telemetry.Diplomacy`.
1584. **Session number.** `session_no` is the larger of the count in the save and the session files of the run on this machine, plus one, so a load of an older save gets a new number.
1585. **Privacy.** Log lines in telemetry files have no user folder name (after `\Users\`, `/Users/`, `/home/`) and no Steam ID (17 digits that start with 7656119): they become `<user>` and `<steam id>`. The session start log line names only the file.
1586. **Blueprint money.** Vanilla charges a blueprint unlock with a direct set of the money (`CommTechsTab.MPBuyTechInput`). Telemetry logs it as `econ.money` with source `tech_unlock` and the tech ID.
1587. **Vault deconstruction.** Crew that take a vault apart are no vault destruction: `tech.vault_hit` has cause `vault_deconstructed` and `destroyed` false, the tech hint is `vault_deconstructed`, and the lost health is no damage in `combat.damage`. Each `tech.vault_hit` names the ship and its player, read before vanilla takes the part off the ship.
1588. **Fights.** `combat.fight` joins damage windows with damage to the players, hunters or hostiles, and wrecks of those sides, until `Telemetry.FightGapSeconds` (90) of game time pass without either, the sector changes, the players jump or the session ends: start, end, sides, damage and wrecks by side, kills, player ship losses and crew deaths. A fight without such damage is dropped.
1589. **Mission time.** `mission.ended` has `duration_s` in run game seconds since the accept. The telemetry save data keeps the accept times, so a load keeps them.
1590. **Loss timer.** `tech.loss_timer` fires when the state changes: `idle`, `running`, or `paused` with the reason (`local_jump`, `jump_limbo`, `ships_elsewhere` with the waiting ships by system) from the same check as the timer (requirement 12, `LossTimer.PauseReason`).
1591. **Real time split.** `perf` and `session.end` split the real time of frames into paused, build mode (not paused) and play, from this machine's view.

Playtest 2026-11-15: a client's telemetry stayed on the client's machine and was lost to the analysis. Requirements 1592, 1593, 1597 bring every player's files to the host. Code: `Telemetry/Relay.cs`, the pure rules in `RelayModel` (`Telemetry/TelemetryModel.cs`).

1592. **Relay to the host.** In co-op each client sends its telemetry files to the host, and keeps its own files as they are. The host writes each one to `telemetry/players/<player name>/<file name>`: the client's file name, in a folder per player (the MP player name, letters, digits, `-` and `_` only). The client sends the files of the current run: every session of the run on its machine, with their parts. Transport: a reliable RPC on a sub-channel of the game's MP connection (like the shared choice hovers, requirement 601), so it skips the input queue and the lockstep. It is no MP input and no sim state, and each machine follows its own `Telemetry.RelayToHost` switch. The host folder trim (`MaxFolderMegabytes`) counts the copies too.
1593. **No byte lost, repeated or mixed.** A file is an append-only byte stream. The client sends one chunk of at most 32 KB at a time, from the length that the host confirmed; the host appends only the bytes past its copy's length and answers with that length. A chunk without an answer goes again after 5 real seconds. After each new connection (a late join, a resync, a load, a reconnect) the client first asks the host for its length of each file, so it sends neither twice nor with a gap. Each file has its own copy in its player's folder, so lines of two players or two sessions never share a file. When a client's game closes, it sends the rest of its files once without waiting for answers. Limit: lines that a client writes after the last chunk that reached the host arrive only at its next join of the same run; a player whose name changes gets a second folder. Tests: unit tests `RelayModelTests` (accept rule, probe, a stream with lost, repeated and late chunks, file and folder names); co-op step `telemetry.relay` in `coop-core`: in 4 KB chunks over the join, the resync and the load, the client's closed files reach the host whole and every copy is a valid client file.
1597. **Pull and report.** `scripts/pull-telemetry.sh` copies the `players/` folders too. The report keeps a client's sessions as a run of their own (`<run> (client <player index>)`), also when the same file comes from the client's machine and from the host, so host and client events never mix.

Playtest 2026-11-15: stays of 58 and 111 minutes per sector, where the balance model assumes 17.5 (BALANCE.md). Before any fix (the storyteller proposal, option L0 "measure first"), requirements 1760 to 1763 record what the time in a system goes to. Pure rules: `TimeUse` in `Telemetry/TelemetryModel.cs`. Signals: `Telemetry/ActivitySignalsReader.cs`.

1760. **Time use.** Each system stay splits its game seconds into six activities of the players' fleet: fight, build, trade, travel, repair and idle. The fleet does one activity at a time: the first of fight, build, trade, travel, repair whose signal is on, else idle. So the six sums add up to the stay (`stay_s`). Next to them, `time_any` holds the seconds that each signal was on at all, also while a higher activity won, so overlaps (repairs during travel) stay visible. The session samples the signals every 0.5 s of sim time; each sample takes the sim seconds since the one before. The sim seconds of the jump itself count as travel of the old stay.
1761. **Signals.** Only state that the game already keeps. Fight: a `combat.fight` (requirement 1588) is open and its last damage window is at most `AccrualSeconds` old. Build: this machine's build tool is open, or a human ship has new parts or doors placed and not built yet (a queued construction that is no rebuild and not blocked by something in the way, also while the crew fetch its resources), or a queued deconstruction. Limit: a placed part or an ordered repair that never gets its resources counts until it is done or removed. Trade: a human ship is in comms with a station or ship (`CareerSimModeManager.OpenComms`), or crew carry a station trade to or from a human ship (`ResourceTransferJob` with a trade type; often the station's crew). Travel: a human ship has a move order to a point at least `Telemetry.TravelMinDistance` (1500) away or to a relay (`FtlGateJumpCommand`), or the fleet does a local FTL jump. Repair: a human ship has part repairs or rebuilds of destroyed parts or doors ordered and not done yet (`QueuedPartRepairs`, `QueuedPartConstruction.IsRepair`), also while the crew fetch the resources. Limit: the build tool is local GUI state, so in co-op each file counts only its own player's editor.
1762. **Events and report.** `run.jump` has `time_use` and `time_any` of the stay, `system.enter` has `prev_time_use` and `prev_time_any`, and each `snap` has `stay_s`, `time_use` and `time_any` of the current stay. The sums count like `stay_s`: from the system entry or the session start, so a load starts them again. The report adds the share of each activity to each row of the Sectors table, a stacked bar per sector visit and a finding with the shares of all stays; it adds the parts of a visit that several sessions hold.
1763. **Tests.** Unit tests `TimeUseTests` (the priority rule, sums that add up to the stay, overlaps) and a report test (shares per visit, session parts added). `telemetry-basic` makes each activity happen once, one after the other (damage to the own ship, the repair button with the test command `telerepair`, a far move order with `telemove`, a sale, a blueprint corridor), and checks the autotest fields `tele_time_<activity>`. The test command `teleactivity` logs the signals of the moment.

Playtest notes (2026-11-23, for the co-op playtests on two Macs). Code: `Telemetry/PlaytestNotes.cs`.

1984. **Note key.** `Telemetry.NoteKey` (default backslash, which vanilla binds to nothing) opens a text dialog over the game, only when no menu or dialog is on top and no text box has the focus (the game's own sign: a focused text box that blocks other input, such as the co-op chat, sets `App.Input.InputFilter`). Enter saves, Escape cancels. A saved note is a `note` event: the text, the player's name, the real time of the key press, and what the player saw (an event page, an open comms window, the build tool, a dialog). A chat line confirms it. Local UI only: no MP input, no sim state. In co-op the game keeps running under the dialog; in single player it pauses, like every vanilla dialog.
1985. **Screenshot.** At the key press, before the dialog draws, the note takes the vanilla end-of-frame capture (`GraphicsManager.GetEndOfFrameScreenShot`, the path of the game's screenshot key; the Mac app implements it too) and saves it as `telemetry/notes/<run id>__<time>.png`. Without a graphics device (headless) or when the capture fails or takes more than 3 s, the note is saved without one (`screenshot` null). A cancelled note deletes its screenshot.
1986. **Co-op.** A client's notes are events of its telemetry file, so they reach the host in `players/<name>/` (requirement 1592), and at once in the host's live notes file (requirement 1988). Screenshots stay on the machine that took them. Test: `telemetry-notes` (sim) opens a note, saves one and cancels one, and counts one `note` event; with a focused text box that blocks other input, the key opens nothing.
1987. **Report.** `hc-telemetry` lists the notes of a run first, in play order (game time, real time, player, system, screen, screenshot, text), then the events within 60 game seconds of each note in the same session, without the frequent kinds (perf, trace, AI switches, damage sums, accruals, snapshots, offers, spawns, tech value steps).
1988. **Live notes file.** Each saved note is also one JSON line in `<mod folder>/telemetry/notes.jsonl` of its machine, written and closed at once, so `tail -F` shows it within a second. A co-op client sends the line to the host at once over the relay channel (a reliable RPC, requirement 1592, also with `RelayToHost` off), and the host appends it to its own `notes.jsonl`. So the host's file holds the notes of every player of the game, in arrival order. The line has the common event fields (requirement 532) and the note fields of requirement 1984, plus `wall_utc`. Test: `telemetry-notes` checks the line; the co-op step `telemetry.note` (`coop-core`) checks that the client's note reaches the host's file.
